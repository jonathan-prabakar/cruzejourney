# Cruze FuelSense telemetry integration (Milestone 2)

The telemetry foundation is independent of dashboard components and needs no backend, network access, API key, or physical OBD adapter. No UI files are included.

## Dataset and units

Import `src/data/demo-telemetry.json` or use `createDemoTelemetryProvider()`.
The envelope is `{ metadata: DatasetMetadata, records: VehicleTelemetry[] }`. All exported types live in `src/lib/telemetry/types.ts`.

| Record field | Unit / contract |
| --- | --- |
| timestamp | ISO date-time with seconds and explicit Z or UTC offset |
| latitude / longitude | Decimal degrees, or null |
| speed_mph | Miles per hour, required |
| rpm | Revolutions per minute, required |
| fuel_percent | 0–100 percent of tank capacity, required |
| mpg | Miles per US gallon, required; zero is accepted for stationary/unknown economy readings supplied by a source |
| coolant_temp_f | Degrees Fahrenheit, or null |
| diagnostic_code | Uppercase OBD code such as P0301, or null; no interpretation |

Metadata requires name, source, synthetic flag, route, limitations array, and vehicle profile (name, tank_capacity_gallons, typical_mpg). Future real data must identify its source and set synthetic appropriately.

There was no dataset in the initial repository. This dataset is **entirely synthetic**, including GPS positions and diagnostic events, reproducibly generated by `node scripts/generate-demo.mjs`. It contains 241 sequential readings of the fictional Demo Freight Truck (120 US gallon tank, typical 8 MPG) traveling a synthetic San Antonio → New Braunfels → San Marcos → Kyle → Austin corridor. Authored geographic anchors approximate the corridor; interpolated positions are **not verified road geometry**, may fall off-road, and must not be presented as actual measured travel.

The trip begins at 17% fuel and naturally drops below 10%; there is no accelerated depletion. Adjacent endpoint speeds are integrated over each timestamp interval; fuel used equals that interval's distance divided by its ending record's MPG. Coordinates interpolate by traveled distance along the corridor. Timestamps are evenly spaced, about 20 seconds apart. RPM, temperature, speed and MPG vary. P0301 appears in records 160–175 (zero based), with no diagnostic interpretation. The truck is already warm and moving at the first reading. The dataset models a trip excerpt rather than ignition/startup/shutdown.

## Loading and validation

```ts
import { TelemetryPlayback, parseTelemetryJson } from './src/lib/telemetry';

const provider = new TelemetryPlayback();
const result = provider.loadDataset(localJsonObject); // or JSON text from a local file
if (!result.valid) {
  // Present result.errors: { index, field, message }.
  // The previous dataset and playback remain untouched.
}
const inspected = parseTelemetryJson(localJsonText);
```

The default factory imports bundled JSON, so no runtime fetch is needed. For a browser file picker, pass `await file.text()` to `loadDataset`. No filesystem-specific code enters the browser bundle.

Validation accepts unknown input, rejects malformed envelopes/rows, invalid calendar dates, missing required values, nonfinite/out-of-bound numbers, and duplicate timestamp instants (including equivalent UTC offsets). Optional missing/null values become null; measurements are never invented. Valid records are copied and sorted chronologically. Errors refer to original zero-based input indices; dataset-level indices are null.

`validateDataset` and `parseTelemetryJson` return normalized valid rows even when other rows are invalid, for inspection. **The playback engine rejects the entire load if any validation error exists**, avoiding silently replaying a partial trip. Empty records arrays are valid when metadata is valid. Validation is structural with broad numeric limits (speed 0–200 MPH, RPM 0–12000, fuel 0–100%, MPG 0–1000, coolant -100–350°F); it does not infer vehicle-specific sensor faults or repair inconsistent measurements. GPS values are validated individually and can independently be null. CSV is intentionally omitted; convert sources to this JSON envelope.

## Playback API

`TelemetryPlayback` implements `TelemetryProvider`.

| Method | Behavior |
| --- | --- |
| loadDataset(input) | Validate parsed JSON or text; valid load replaces data, resets to first record, retains selected speed |
| play() | Start/resume; repeated calls do not create extra timers; ended/empty is a no-op |
| pause() | Capture exact elapsed dataset time and stop timers |
| reset() | Stop and return to first record (ready); retain selected speed |
| setPlaybackSpeed(1 \| 2 \| 5) | Preserve elapsed time and reschedule remaining interval |
| seekTo(index) | Seek to an integer record index; preserve playing mode, otherwise pause; final record ends playback |
| getCurrentTelemetry() | Current frozen reading or null |
| getPlaybackState() | Frozen sampled state: status, speed, index, total, progress, elapsed_ms, duration_ms |
| getSnapshot() | Stable frozen telemetry/playback snapshot for React external stores |
| subscribe(listener) | Subscribe to data/control changes; returns an unsubscribe function |
| unsubscribe(listener) | Remove a subscriber explicitly |
| dispose() | Terminal, idempotent timer/subscription cleanup |

Playback statuses: empty, ready, playing, paused, ended. Empty datasets have index -1 and progress 0. Progress is elapsed timestamp duration divided by total timestamp duration; a singleton has progress 1. At the end, call reset then play to restart, or seek to an earlier record. Invalid speed/index inputs throw RangeError; the dashboard should constrain controls. Mutation and subscription after dispose throw; getters remain available.

The first reading is visible immediately. Later readings respect relative timestamps and selected playback speed. Mid-interval pause/resume and speed changes retain elapsed time. A delayed timer catches up to the latest due record; it does not replay every missed intermediate event to subscribers. Progress updates at timestamp boundaries and controls, not animation frames. Returned objects must be treated as immutable.

A `PlaybackScheduler` (monotonic now, setTimeout, clearTimeout) can be injected for deterministic testing. Default timing uses performance.now. Optional second constructor argument receives subscriber errors; the default isolates/ignores subscriber exceptions so one consumer cannot interrupt playback.

## React adapter

`src/hooks/useVehicleTelemetry.ts` uses useSyncExternalStore, stable controls, and automatic subscription cleanup. Pass one stable provider shared by consumers; avoid recreating it on render. The owner controls its lifecycle; unmounting one consumer does not stop playback for others. Hook subscription cleanup works under React Strict Mode.

Example for a client-only dashboard entry point (adapt imports to its location):

```tsx
import { createDemoTelemetryProvider } from './src/lib/telemetry';
import { useVehicleTelemetry } from './src/hooks/useVehicleTelemetry';

// Create once in the client application's composition root, outside render.
// Dispose at application teardown, after consumers have unmounted.
const provider = createDemoTelemetryProvider();

export function DashboardTelemetryExample() {
  const { telemetry, playback, play, pause, reset, setPlaybackSpeed, seekTo } =
    useVehicleTelemetry(provider);

  return (
    <>
      <output>{telemetry?.speed_mph ?? '—'} mph</output>
      <output>{telemetry?.fuel_percent.toFixed(1) ?? '—'}%</output>
      <output>{Math.round(playback.progress * 100)}%</output>
      <button onClick={play}>Play</button>
      <button onClick={pause}>Pause</button>
      <button onClick={reset}>Reset</button>
      <button onClick={() => setPlaybackSpeed(2)}>2×</button>
      <button disabled={playback.total === 0} onClick={() => seekTo(0)}>First reading</button>
    </>
  );
}
```

For SSR, use a provider per request/client instance with the same initial dataset on server and client; never share a playing singleton across requests. In server-component frameworks mark the adapter's importing boundary as a client component.

Replace each existing mock value directly: speed → speed_mph, tachometer → rpm, fuel gauge → fuel_percent, economy → mpg, temperature → coolant_temp_f, map marker → latitude/longitude (only when both are non-null). Display missing values as unavailable; do not substitute zero. diagnostic_code is a raw code only. Fuel range, recommendations, code interpretation, and derived efficiency features remain later milestones.

### Milestone 1 checklist

- Bring over src/data, src/lib/telemetry, src/hooks/useVehicleTelemetry.ts, and this guide.
- Reconcile package.json/lockfile/tsconfig with your app: these were bootstrapped because origin/main contained only README.md. Preserve your framework scripts; add test tooling and JSON imports as needed. No dashboard dependencies or layouts were assumed.
- Create a stable provider in the client composition root; pass it to telemetry consumers.
- Replace mock display values with typed fields; handle null readings.
- Bind controls to play/pause/reset, supported speeds and integer indices in [0, total - 1].
- Keep the synthetic source/route disclaimer visible wherever data provenance matters.
- Dispose the provider when its owner is permanently torn down; unmounting individual consumers only unsubscribes them.
- Verify initial, low-fuel and raw-code scenarios using seek controls, then run checks below.

## Verification and limitations

Node 22.19+ is recommended. From the repository root:

```sh
npm ci
npm test
npm run typecheck
npm run lint
npm run build
node scripts/generate-demo.mjs  # optional deterministic regeneration
```

Tests cover validation, missing/invalid fields, sorting and duplicate instants, timestamp-based chronological playback, pause/resume, reset, 1×/2×/5× speeds, seek, end, empty/singleton datasets, replacement loads, subscribers, timers, delayed scheduler callbacks, React unmount/Strict Mode, and synthetic fuel/GPS consistency.

Build emits a TypeScript library and declarations into ignored dist/; this repository has no dashboard or production web application to build. Source imports are intended for the dashboard's bundler; dist/ is not a standalone Node package. There is no CSV adapter, live vehicle connection, interpolation between readings, road routing service, or implementation from Milestones 3–6.

The complete dependency audit still reports 11 moderate findings in the development-only ESLint/typescript-eslint chain through minimatch; the latest installed upstream tools still depend on the affected major version. No forced major-version transitive override was applied. The React adapter test uses react-test-renderer (deprecated upstream), only as a development dependency.
